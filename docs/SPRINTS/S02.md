# Objetivo

Realizar el levantamiento funcional completo del módulo Servicio Técnico antes de iniciar cualquier desarrollo, respetando la metodología de producción del proyecto DarlexPC.

El objetivo principal fue comprender el flujo real de trabajo utilizado actualmente en el negocio, identificar necesidades operativas, definir el alcance inicial del módulo y establecer las bases funcionales para su desarrollo.

---

# Trabajo realizado

Durante este Sprint se analizaron los procesos actuales del área de Servicio Técnico y se definieron los siguientes aspectos:

## Flujo actual del negocio

Se documentó el proceso utilizado actualmente mediante formularios físicos en Microsoft Word.

Proceso identificado:

1. El cliente entrega el equipo.
2. Recepción consulta la falla reportada.
3. Se registran datos del cliente.
4. Se registran datos del equipo.
5. Se registran accesorios entregados.
6. El cliente firma el documento.
7. Se imprimen dos copias.
8. Una copia queda para el cliente.
9. Una copia permanece en Servicio Técnico.

Se identificó como principal problema la dependencia del soporte físico (papel), provocando pérdida de órdenes, acumulación documental y dificultad para el seguimiento.

---

## Flujo digital propuesto

Se acordó mantener exactamente el mismo flujo operativo utilizado actualmente, sustituyendo únicamente el formulario físico por un registro digital.

Nuevo flujo:

Recepción

↓

Registro digital

↓

Generación automática de número de orden

↓

Impresión del comprobante para el cliente

↓

La orden permanece almacenada digitalmente

↓

Servicio Técnico trabaja sobre la misma orden

↓

Recepción realiza el despacho

↓

La orden queda registrada en historial

---

## Roles funcionales

Se definieron tres perfiles principales:

### Recepción

- Registrar órdenes.
- Buscar órdenes.
- Imprimir comprobantes.
- Entregar equipos.
- Realizar despacho.

### Técnico

- Consultar órdenes.
- Registrar diagnóstico.
- Registrar reparación.
- Registrar tiempos estimados.
- Registrar utilización de repuestos.
- Cambiar estado de la orden.

### Administración

Acceso completo al sistema incluyendo futuras funciones administrativas.

---

## Estados de una Orden

Se aprobaron los estados iniciales del flujo operativo:

- Ingresado
- En diagnóstico
- Esperando aprobación
- Esperando repuestos
- En reparación
- Listo para retirar
- Entregado
- Anulada

---

## Wireframe funcional

Se definió un primer bosquejo funcional basado en el formulario utilizado actualmente por el negocio.

La prioridad será mantener una interfaz conocida para minimizar la curva de aprendizaje del personal.

El diseño conservará:

- Datos del cliente.
- Datos del equipo.
- Accesorios.
- Falla reportada.
- Observaciones.
- Descargo de responsabilidad.
- Impresión del comprobante.

---

## Flujo interno del módulo

Se identificaron tres etapas funcionales:

Recepción

↓

Servicio Técnico

↓

Despacho

Cada etapa trabajará sobre la misma orden sin duplicar información.

---

## Seguimiento de órdenes

Se definió que el sistema deberá mostrar visualmente:

- Nuevos ingresos.
- Equipos en reparación.
- Equipos listos para despacho.
- Equipos pendientes de retiro.

También se propuso un seguimiento por antigüedad utilizando indicadores visuales para órdenes listas que aún no han sido retiradas por el cliente.

---

## Gestión de órdenes

Se acordó permitir:

- Corrección de información mientras la orden permanezca activa.
- Anulación controlada de órdenes creadas por error.

No se permitirá la eliminación física de registros para preservar la trazabilidad.

---

## Arquitectura preliminar

Se decidió mantener completamente independiente el módulo Servicio Técnico respecto al Ecommerce.

Arquitectura propuesta:

Frontend

HTML + CSS + JavaScript

↓

Cloudflare Worker

↓

Cloudflare D1

El catálogo continuará utilizando Google Sheets.

Servicio Técnico utilizará una base de datos independiente.

# Observaciones

El módulo dejó de concebirse como un formulario digital para convertirse en un sistema completo de gestión del ciclo de vida de una orden de Servicio Técnico.

La prioridad del proyecto será digitalizar el proceso existente sin alterar la forma de trabajo del negocio.

---

# Problemas encontrados

- Dependencia del soporte físico.
- Pérdida de órdenes impresas.
- Acumulación de documentos.
- Dificultad para realizar seguimiento de equipos.
- Ausencia de estados internos.
- Falta de historial centralizado.

---

# Solución aplicada

Se definió un flujo digital que conserva el procedimiento operativo actual, agregando:

- Persistencia digital.
- Estados de trabajo.
- Seguimiento.
- Preparación para autenticación.
- Preparación para auditoría.
- Escalabilidad mediante Cloudflare D1.

---

# Decisiones del Sprint

## Separación de módulos

Se establece que Servicio Técnico será un módulo independiente del Ecommerce.

Motivo:

Evitar acoplamiento entre ventas y postventa.

---

## Base de datos independiente

Se adopta Cloudflare D1 como objetivo para este módulo.

Motivo:

Separar información sensible del catálogo público y validar la viabilidad de una base de datos SQL dentro del ecosistema DarlexPC.

---

## Conservación del flujo del negocio

El sistema deberá adaptarse al proceso operativo existente y no obligar al personal a cambiar su forma de trabajo.
